### Task 3 — cache-line contention

Six platform threads, each doing exactly **50,000,000 increments**. Unpadded storage is a `long[] sharedCounts` of length six. The padded version spaces active indices eight `long`s apart (**64 bytes**). Both variants use the **same VarHandle opaque read/write loop**, so the padding experiment does not change synchronization strength or replace one loop with an optimizable local `counter += iterations`. One thread owns each active element; every final count is verified after completion.

| Variant | Median of 3 trials |
|---|---:|
| Unpadded Shared | 263.619900 ms |
| Padded | 24.179200 ms |
| Unpadded / Padded ratio | **10.9028x** |

Workers start from a common latch; timing includes release, increments and final joins, excluding pool startup. Variant order alternates across trials. A 64-byte cache line is assumed for this experiment; CPU placement is left to the OS. This is a timing demonstration consistent with false sharing, not a hardware-counter measurement of invalidations.

Declaring only the **array reference** `volatile` would not make its elements volatile. The new benchmark instead addresses elements through a `VarHandle` with explicit access semantics. Opaque accesses are coherent per variable without imposing a global volatile ordering on unrelated counters.

|---|---:|---:|

All three trials record every worker's completion offset, item count and requested sleep sum, and verify each index was visited exactly once. Completion delta is `max(worker_finished)-min(worker_finished)` relative to the same release epoch, not total wall time minus an average.

The prescribed repeating workload is already nearly balanced: static block costs are 232.5, 242.5, 232.5 and 242.5 ms. ### Task 5 — parallel overhead and the sampled crossover

Operation: `y[i] = 2.5*x[i] + 1.25`, using all 12 logical cores in a persistent pool. Each size gets warmup and 15 paired trials, with alternating serial/parallel order. Output arrays are allocated and first-touched before timing; every final output element is checked against the formula. Serial and parallel operate on the same input with separate output arrays.

| N | Serial median (ms) | Parallel median (ms) | Speedup | Parallel status |
|---:|---:|---:|---:|---|
| 100 | 0.000200 | 0.039200 | 0.0051x | SLOWER |
| 1,000 | 0.000400 | 0.024900 | 0.0161x | SLOWER |
| 10,000 | 0.002100 | 0.022600 | 0.0929x | SLOWER |
| 100,000 | 0.029400 | 0.048000 | 0.6125x | SLOWER |
| 1,000,000 | 0.434400 | 0.349500 | 1.2429x | **FASTER** |
| 10,000,000 | 6.253500 | 6.426900 | 0.9730x | SLOWER |

The script programmatically reports the observed **SLOWER → FASTER bracket: `100000 < N <= 1000000`**. It also reports the **FASTER → SLOWER reversal: `1000000 < N <= 10000000`**. This largest-size result is close to parity and should not be treated as a statistically established universal regression.

Six sampled sizes can establish an interval, **not an exact element-level tipping point or a permanently monotonic crossover**. These raw timings support the reported classifications for this run; they do not isolate bandwidth, cache state, thermal changes or OS interference as the cause of the reversal. The code handles no crossover and multiple crossings rather than assuming a favorable result. Pool creation is excluded intentionally; including startup would answer a different, end-to-end question and generally increase overhead.

### Task 6 — synchronization cost and data loss

Four platform threads each attempt **2,000,000 increments**, for an expected final count of **8,000,000**. Each variant starts with a fresh zero-valued counter. The unsafe version uses an ordinary shared `int` and `counter++`, with no locks, volatile accesses, atomics, sleeps or yields in its increment loop. The correct version uses `AtomicInteger.incrementAndGet()` on a shared atomic counter. Start/finish coordination is outside the loops and does not protect the unsafe increments.

| Trial | Unsafe actual | Unsafe updates lost | Atomic actual | Unsafe wall (ms) | Atomic wall (ms) | Atomic minus unsafe (ms) |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 3,216,641 | 59.791988% | 8,000,000 | 0.095800 | 67.373300 | +67.277500 |
| 2 | 2,861,793 | 64.227588% | 8,000,000 | 0.208000 | 58.551200 | +58.343200 |
| 3 | 2,860,449 | 64.244388% | 8,000,000 | 0.212800 | 66.425000 | +66.212200 |
| 4 | 2,809,474 | 64.881575% | 8,000,000 | 0.162600 | 62.637300 | +62.474700 |
| 5 | 3,138,498 | 60.768775% | 8,000,000 | 0.113100 | 64.102600 | +63.989500 |

- Lost updates: `100.0 * (expected - actual) / expected`; every atomic run records **0% loss** and verifies its exact final count.
- Median unsafe time: **0.162600 ms**; median atomic time: **64.102600 ms**.
- Synchronization penalty, difference of medians: **+63.940000 ms**, or **394.2349x** atomic/unsafe wall time (**+39323.4932%** relative overhead).
- Median of the five paired penalties: **+63.989500 ms**. This is explicitly distinguished from the difference of medians.

The benchmark performs warmup, then five paired trials with alternating variant order. Pool startup is excluded; timed work includes the common latch release, the increment loops and final future joins. The raw output retains every count, percentage, wall time in milliseconds and nanoseconds, and the raw timing arrays. Earlier task logs remain unchanged.

**Interpretation:** this is a deliberately incorrect implementation compared with a correct one, not equivalent successful work. Plain racy loops may be coalesced or otherwise optimized by the JVM, so their very short times do not prove that all source-level increments became individual memory operations. `AtomicInteger` supplies atomic operations without an explicit mutex/monitor; the reported penalty is the measured cost of these implementations, **not isolated lock-acquisition latency**. The race outcome is nondeterministic, and a run with no observed loss would not prove safety. No retries, artificial interleaving or expected-loss test is used to force a favorable demonstration.

### Task 7 — arithmetic intensity versus memory bottlenecks

Both kernels use the **same 30,000,000-element float64 input** generated with student-ID seed **230103341**, and a distinct output array. Their total payload is **480,000,000 bytes** (approximately 458 MiB), much larger than the CPU cache sizes recorded in the root README. Input values are uniform in [0,1), with angles in radians, avoiding tangent singularities.

- **Kernel A:** explicit vector-copy loop `B[i] = A[i]`, no floating-point arithmetic per element.
- **Kernel B:** `B[i] = Math.sin(A[i])*Math.cos(A[i]) + Math.tan(A[i])`, without an algebraic shortcut. The expensive transcendental functions make this a higher-computation-per-byte comparison; no fixed FLOP count is assigned to a transcendental function.

| Kernel | Worker count | Median wall (ms) | Speedup | Efficiency = speedup/workers | Useful GB/s |
|---|---:|---:|---:|---:|---:|
| A — copy | 1 | 26.987900 | 1.0000x | 100.0000% | 17.7857 |
| A — copy | 2 | 20.952200 | 1.2881x | 64.4035% | 22.9093 |
| A — copy | 12 | 21.416500 | 1.2601x | 10.5012% | 22.4126 |
| B — compute | 1 | 1301.802300 | 1.0000x | 100.0000% | 0.3687 |
| B — compute | 2 | 718.964900 | 1.8107x | 90.5331% | 0.6676 |
| B — compute | 12 | 234.551600 | 5.5502x | 46.2515% | 2.0465 |

**Observed conclusion: Kernel A (copy) stalled in scaling beyond two workers, consistent with memory-channel saturation.** Its useful throughput stays near **22–23 GB/s**, with a **0.9783x** gain from 2 to 12 workers. Kernel B continues to scale over that interval, gaining **3.0653x**, and does not exhibit the same plateau. The script selects its wording from the measured results, rather than unconditionally asserting saturation: its explicit stall heuristic is a gain of **at most 1.20x** from 2 to max workers. This threshold is a reporting heuristic, not a statistical test. It also handles a compute plateau or an absent copy plateau honestly on other runs.

**Method:** seven measured trials per configuration after short-loop and full-array warmup. Worker-count order rotates each trial, and kernel order alternates. All configurations, including one worker, time task submission, kernel execution and future joins in prestarted persistent pools; generation, allocation and validation are excluded. Workers process disjoint contiguous partitions, so no output locks are required. Only one kernel/configuration is active at a time. Before every measured pass the same output buffer is reset to NaN outside the timed interval, providing consistent output initialization and allowing missing writes to be detected. There is no explicit cache flush or CPU-affinity pinning.

The final pass of **each** kernel/worker combination is checked across **all 30,000,000 elements** outside timing. Copies must match the original bits; compute output is checked against the scalar `StrictMath` formula using the shared numerical tolerance `max(1, abs(expected))*1e-11`. Other trials receive sampled checks. The saved stdout includes every raw timing sample in nanoseconds, formulas, efficiency units, useful bandwidth and the conditional conclusion. Earlier task logs remain unchanged.

**Limits:** useful GB/s counts only **8 bytes read + 8 bytes written per element**, divided by elapsed time, in decimal GB/s. It is not measured physical DRAM traffic: write allocation, cache effects and other bus traffic are omitted. No RAM-controller counters, theoretical/independently measured bandwidth ceiling, CPU frequency trace or thermal telemetry were collected. Thus the plateau is **evidence consistent with**, not proof of, memory-channel saturation; the benchmark does not establish which or how many physical channels are saturated. SMT (12 logical workers on six physical cores), OS interference and JVM-generated code can also affect efficiency. Raw timings vary visibly across trials; these medians are descriptive, not confidence intervals.
